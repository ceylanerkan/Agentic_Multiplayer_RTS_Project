# Autopilot instructions

These are the instructions for the daily cloud agent that helps the (single) student finish this CSE-377
project before the deadline on **2026-11-30**. The agent runs once a day at about 03:00 Istanbul time
(00:00 UTC) from 2026-11-11 to 2026-11-29. Each run lasts about one hour. Do not edit this file during a run.

| File | Written by | Purpose |
|---|---|---|
| `docs/nightly-plan.md` | the student; you only tick items | What to do each night, from 2026-11-12 to 2026-11-29. |
| `UNITY_FEEDBACK.md` (on `main`) | the student | Unity errors, bugs, answers to your questions, test results. **Never edit it**: the student owns it, and editing it on your branch causes merge conflicts. |
| `MORNING.md` | you | Today's brief for the student, in Turkish. Rewrite it completely on every run (section 6). |
| `docs/progress-log.md` | you | History of all runs, newest first, in English. |
| `TODO.md` | you | Remaining work only. |

## 1. Before you start
1. If today's UTC date is after 2026-11-29, stop immediately without changing anything.
2. Git:
   - Work on the branch `autopilot`. If `origin/autopilot` exists, check it out; otherwise create it from
     `origin/main`.
   - Merge `origin/main` into it. The student pushes Unity editor work and `UNITY_FEEDBACK.md` to `main`, and
     usually merges your pull request every morning.
   - On conflicts, keep `main`'s version of Unity editor files (`*.unity`, `*.prefab`, `*.asset`, `*.meta`,
     `ProjectSettings/`) and of `UNITY_FEEDBACK.md`, and merge code by hand. If you cannot resolve a conflict
     safely, abort the merge, work without it, and report it in `MORNING.md`.
   - Never push to `main`, never force-push, never rewrite history.
3. Read `docs/nightly-plan.md`, `README.md`, `docs/design-brief.md`, `TODO.md`, `docs/setup.md`, the previous `MORNING.md` and the newest
   entries of `docs/progress-log.md` (if they exist), and `UNITY_FEEDBACK.md`. The assignment PDF is not in the
   repository; `TODO.md` and the design brief already contain its requirements.

## 2. Pick today's work
1. **First**, handle the new entries in `UNITY_FEEDBACK.md`. Entries are grouped under date headings; the
   progress log lists the headings you already handled, so skip those.
   - Errors and bugs: fix them.
   - Answers to your questions (by id, for example `Q-1114-1: B`): apply them.
   - Test results for **[You]** tasks: remove passed tasks from `TODO.md`; turn failures into fixes.
2. Then follow `docs/nightly-plan.md`:
   - Start with the **earliest night that still has an unchecked item**, even if its date has passed, and do its
     items in order.
   - When that night is done, continue with the next night's items, and so on.
   - When every night is done, use the plan's "When the plan is finished early" list.
3. The run lasts one hour. Run `date -u` at the start and between chunks.
   - **Keep working until about 50 minutes have passed.** None of these is a reason to stop early: tonight's
     items are done, a chunk feels complete, or the remaining work needs the Unity editor (section 3 explains how
     to handle that). Stop early only when the whole plan and its "finished early" list are done, or when a usage
     limit stops you.
   - Work in chunks: one coherent piece that is finished and tested, not many half-done items.
   - After each chunk, update `docs/nightly-plan.md`, `TODO.md`, `docs/progress-log.md` and `MORNING.md`, then
     commit and push (section 7). That way nothing is lost if a usage limit cuts the run off.
   - Do not start a new chunk after about 50 minutes. Finish by about 60 minutes.
   - Save usage: read only the files you need, read large files in parts, and keep command output short (for
     example `pytest -q`, `| tail -n 40`).

## 3. How to write the code
**General**
- All game numbers come from `ai/rag/knowledge/*.json`. Never hard-code different values.
- The student must explain the code in an oral defense. Keep it simple and readable, with short comments that
  explain *why*, not *what*.
- Never commit secrets: no API keys, no `.env`, no `PhotonAppSettings.asset`.

**Python (`ai/`, `evaluation/`)**
- Python 3.10+. Add dependencies to `ai/requirements.txt` with versions.
- Write pytest tests and run them. All tests must pass before you commit.
- Tests never call a real LLM: mock Gemini. There is no API key in this environment.

**Unity C# (`UnityRTS/Assets/Scripts/`)**
- Unity 6000.4, Photon Fusion 2.0.13, Host Mode. The host has state authority; clients send commands through
  `CommandRelay` RPCs (design brief §3).
- You cannot run Unity here. That is **not** a reason to skip a script: write the MonoBehaviour, NetworkBehaviour
  and UI scripts in full, then add **[You]** steps that say exactly how to wire them in the editor. The student
  tests them the next day and reports problems in `UNITY_FEEDBACK.md`. To catch errors without Unity:
  - Put pure game rules (costs, population, prerequisites, damage, visibility, the validator) in plain C# classes
    in `Assets/Scripts/Core` (assembly `RTS.Core`, no `UnityEngine`) where practical, and cover them with EditMode
    tests under `UnityRTS/Assets/Tests/EditMode/`.
  - If `dotnet` is missing, install it once per run:
    `curl -sSL https://dot.net/v1/dotnet-install.sh | bash -s -- --channel 8.0 --install-dir /tmp/dotnet`, then
    use `/tmp/dotnet/dotnet`. Compile `Assets/Scripts/Core` and the EditMode rule tests (with the NUnit package) in
    a throwaway project outside the repository. If the install fails, continue without it and say so in
    `MORNING.md`.
  - Use only Fusion 2 APIs you are sure exist (`NetworkBehaviour`, `[Networked]` properties, `[Rpc]` with
    `RpcSources`/`RpcTargets`, `NetworkRunner.StartGame` with `GameMode.Host`/`GameMode.Client`,
    `Runner.Spawn`, `HasStateAuthority`, `HasInputAuthority`). When unsure, check
    https://doc.photonengine.com/fusion/current/ instead of guessing.
- Do not write `.meta` files, scenes, prefabs or other editor assets by hand; Unity creates them. Anything that
  needs the editor (scenes, prefabs, NavMesh bake, adding components and setting fields, play testing) is the
  student's job.

## 4. Decisions and uncertainty
- **Critical decision**: hard to undo, or it changes the design brief, the schemas, game numbers, the
  networking/authority model, the scope (adding or removing a feature), or anything graded. Do not decide it
  yourself. Ask it in `MORNING.md` and work on other items until the student answers.
- **Small decision**: easy to change later (names, file layout, UI layout, internal helpers). Choose the simplest
  option that fits the design brief and list it in `MORNING.md` under "Gözden geçir".
- When you are unsure or confused (an unclear requirement, a Fusion API you could not verify, code that may not
  compile), say so in `MORNING.md` under "Emin olmadığım yerler". Do not hide it.

## 5. Update the plan
- In `docs/nightly-plan.md`, mark each agent item you fully finished as `[x]` and add the run date, for example
  `(done 2026-11-12)`. If an item is only partly done, leave it unchecked and add a short note under it. Do not
  otherwise change the plan; if an item is impossible or much too big, say so in `MORNING.md`. If this file has a
  merge conflict, take `main`'s version and apply your ticks again.
- `TODO.md` lists only remaining work. Remove the items you fully finished.
- When you wrote code that still needs editor work or testing, replace the item with a student task that starts
  with **[You]** and says exactly what to do in the Unity editor: which scene, which GameObject, which components
  and which field values.
- Video, slides, the Windows build, MCP Inspector screenshots and the live Gemini evaluation run are always
  **[You]** tasks.
- Keep one entry per run at the top of `docs/progress-log.md` (create the file if missing) and update it after
  each chunk: the date, what you did, the tests you ran and their results, the `UNITY_FEEDBACK.md` headings you
  handled, open question ids, and known risks.

## 6. Write `MORNING.md`
Rewrite it completely on every run, and update it after each chunk. Write it in Turkish (keep code, file and API names in English), short and
concrete, with exactly these sections:

```markdown
# Sabah notları – <YYYY-MM-DD>

## Dün gece ne yaptım
3–6 short bullets.

## Plan durumu
2–3 lines: which nights of docs/nightly-plan.md are done, how many days you are ahead of or behind its dates,
and which items you will do next night.

## Bugün test et
Numbered steps the student can finish in 15–30 minutes:
1. Merge the pull request on GitHub (give its link), then run `git pull` on main.
2. Which scene to open, what to set up or click, and the expected result.
3. What to write into UNITY_FEEDBACK.md if something fails.
If there is nothing to test, write "Bugün test edilecek bir şey yok."

## Senin kararın gerekiyor
For each critical question: an id (Q-MMDD-n), the question in one sentence, the options with their
consequences, your recommendation, and what is blocked until the student answers. Carry over every unanswered
question from the previous MORNING.md. If there are none, write "Yok."

## Gözden geçir
Small decisions you took on your own. If none, write "Yok."

## Emin olmadığım yerler
Uncertainties, risks, code that may not compile. If none, write "Yok."

## Nasıl cevap verirsin
UNITY_FEEDBACK.md dosyasına bugünün tarihiyle bir başlık aç, cevapları yaz (ör. `Q-1114-1: B`,
`Test 2 tamam`, Console hataları) ve main'e push'la. Bir sonraki gece önce bunları işlerim.
```

## 7. Push after every chunk
1. Commit with clear messages and push `autopilot`.
2. After the first push of the run: if no open pull request from `autopilot` to `main` exists, open one titled
   "Autopilot: daily progress" (with `gh pr create` or whatever GitHub tool is available). If you cannot open a
   pull request, say so in `MORNING.md`.
3. At the end of the run, add a comment to the pull request that summarises the run.
